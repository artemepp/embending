# Семантический поиск по коду: сравнение embedding-моделей

Исследовательский проект: сравниваем три embedding-модели в задаче семантического поиска по корпусу функций на Python и Java. Запросы пишутся на русском и английском языках. Качество оценивается по метрикам **Precision@5** и **MRR**.

Вся работа находится в одном ноутбуке: `semantic_search_research.ipynb`.

## Результаты

Корпус: 200 функций, запросов: 25 (15 на русском, 10 на английском).

| Модель | Размер вектора | Precision@5 | MRR |
|--------|:--------------:|:-----------:|:---:|
| `paraphrase-multilingual-MiniLM-L12-v2` | 384 | 0.88 | 0.609 |
| **`paraphrase-multilingual-mpnet-base-v2`** | 768 | **0.92** | **0.618** |
| `krlvi/sentence-t5-base-nlpl-code_search_net` | 768 | 0.52 | 0.365 |

Метрики по языку запроса:

| Модель | P@5 (EN) | P@5 (RU) | MRR (EN) | MRR (RU) |
|--------|:--------:|:--------:|:--------:|:--------:|
| MiniLM-Multilingual | 0.90 | 0.87 | 0.658 | 0.577 |
| MPNet-Multilingual | 0.90 | 0.93 | 0.617 | 0.620 |
| CodeSearch-T5 | 0.80 | 0.33 | 0.527 | 0.257 |

### Главные выводы

- **MPNet** показала лучший результат и стабильно работает на обоих языках запроса.
- **CodeSearch-T5**, обученная специально на коде, сильно проседает на русских запросах (P@5 падает с 0.80 до 0.33), потому что училась почти только на английском. Для смешанных по языкам запросов мультиязычность важнее специализации на коде.
- **Двуязычные близнецы.** У 95% функций в корпусе есть пара на другом языке (например, `verify_jwt_token` и `verifyJwtToken`) с почти таким же эмбеддингом. В 14 из 24 вопросов близнец оказался выше правильного ответа в выдаче, и это основной источник ошибок.
- Лучшая модель не нашла правильный ответ в топ-5 всего в 2 запросах из 25. Обе ошибки из категорий «Аутентификация и авторизация» и «Утилиты и хелперы».
- Фильтр по языку запроса не вводился сознательно: цель была проверить модели в честных условиях.

## Данные

Три JSON-файла, которые лежат рядом с ноутбуком:

| Файл | Что внутри |
|------|-----------|
| `code_corpus.json` | 200 функций (100 Python + 100 Java): `id`, `function_name`, `description`, `code`, `language`, `category` |
| `eval_questions.json` | 25 вопросов: `query`, `language` (ru/en), `correct_chunk_id` |
| `categories.json` | 5 категорий: ключ, название, цвет для графиков |

Категории: аутентификация и авторизация, работа с базой данных, HTTP-клиенты и API, утилиты и хелперы, валидация и парсинг (по 5 вопросов на каждую).

Перед началом работы ноутбук проверяет целостность данных: количество функций и вопросов, уникальность ID, наличие всех `correct_chunk_id` в корпусе.

## Как это работает

1. Каждая функция превращается в текст формата `"{function_name}: {description}\n{code}"`.
2. Модель считает эмбеддинги документов и запросов, векторы нормализуются (L2).
3. Для каждого запроса считается косинусное сходство со всеми документами.
4. По рейтингу считаются Precision@5 (правильный документ в топ-5) и MRR (среднее обратного ранга правильного документа).

Эмбеддинги кэшируются в `embeddings_cache/*.npy`. Если вы изменили данные, **удалите папку `embeddings_cache`**, иначе подтянутся старые векторы.

## Запуск

Нужен Python 3.10+.

1. Создайте и активируйте виртуальное окружение (по желанию):

```bash
python -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate
```

2. Установите зависимости из `requirements.txt`:

```bash
pip install -r requirements.txt
```

3. Запустите ноутбук:

```bash
jupyter notebook semantic_search_research.ipynb
```

Запустите ячейки по порядку. При первом запуске модели скачиваются с Hugging Face, а эмбеддинги считаются и сохраняются в кэш. При повторных запусках всё берётся из кэша. Для воспроизводимости зафиксирован `RANDOM_STATE = 42`.

При запуске создается папка `embeddings_cache/` в ней хранится кэш эмбеддингов (`corpus_*.npy`, `queries_*.npy`) |

## Ограничения

- Маленькая выборка: 25 вопросов, поэтому один вопрос меняет Precision@5 на 0.04. Различия между MiniLM и MPNet (0.88 против 0.92) статистически не подтверждены.
- Один правильный ответ на вопрос: близнец на другом языке не считается верным, хотя по смыслу это та же функция.
- Корпус синтетический и небольшой, на реальных репозиториях результаты могут отличаться.

## Идеи для развития

- Учитывать близнецов как верные ответы (или схлопывать пары в один документ).
- Добавить фильтр или буст по языку программирования.
- Увеличить набор вопросов и добавить доверительные интервалы.
- Проверить мультиязычные модели побольше (например, E5 или BGE-M3) и перевод запросов перед поиском.
